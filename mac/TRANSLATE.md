## 한 줄 결론

**문단이 밀리거나 섞이는 문제는 없었다(28기사·1003문단·묶음 89개 모두 문단 수 일치).**
이상하게 보이는 까닭은 ① **엔진 자체의 낱말·이름 오역**(Google: midterms→'중간고사', 기기 내: 이름 음역이 섞이고 오타·뜻 뒤집힘),
② **기기 내 번역이 느림**(부하가 높은 이 Mac 에서 기사 하나 37~389초 — 그동안 원문이 보임),

①은 엔진을 바꾸지 않는 한 완전히는 못 고치고, ②·③과 표시 방법은 고칠 수 있다.

## 어떻게 쟀나

- 시험 장치: `Tests/DropcapTests/TranslateProbeTests.swift` (환경변수가 있을 때만 돎). 빠른 길(스크립트 없음)로 본문을 추리고
  `ArticleService.run` 과 같은 순서(제목+첫 8문단 → 나머지, `pre` 제외, 한글 20% 미만만)로 **앱과 같은 Google 묶음 길**을 그대로 따라 보낸 뒤,
  문단별로 `원문 · 묶음 결과 · (선택)문단 하나만 보낸 결과 · (선택)기기 내 번역` 을 JSON 으로 남긴다.
  ```
  DROPCAP_TRANSLATE_PROBE=<결과 폴더> DROPCAP_TRANSLATE_PROBE_URLS=<주소 목록> \
    bugak run --heavy -- swift test --filter TranslateProbeTests
  ```
  주소 줄 끝에 ` ref` 를 붙이면 문단별 단독 번역(기준), ` apple` 이면 기기 내 번역도 받는다. 요청 사이 0.35초를 띄운다.
  결과에는 기사 본문이 들어가므로 저장소에 올리지 않는다.
- 표본: 대상 기사 1 + READSWEEP 해외 영어 기사 27 = **28건**(AI 회사 공지·블로그 12, 기술 매체 5, 종합·경제 뉴스 8, 과학 2, 실시간 블로그 1).
  기사 단독 번역 기준(ref) 5건, 기기 내 번역 비교 9건.
- 이 Mac 은 **영어→한국어 기기 내 번역 자료가 받아져 있음**(`installed`) → 앱은 이 Mac 에서 **기기 내 번역(Apple)** 을 쓴다.
  다른 Mac(자료 없음)이면 Google 이다. 사용자가 본 화면이 어느 엔진인지는 읽기 창 머리의 번역 방식 표시로 알 수 있다.

## 해외 출처 점검(sources-audit)의 '번역' 칸과 겹치는 것

작업자 SrcINTL1·SrcINTL2 가 매체별로 적은 번역 위험(번역은 돌리지 않고 구조로 본 것)은 모두 **추리기 쪽**이라 위 케이스 7·8 과 같은 갈래다.
Reader 담당 인계에 함께 넣는다.

- 번역기에 들어가면 안 되는 조각: iframe 코드 글(NPR — 이 점검에서도 확인), `[email protected]`(TechCrunch), `[[duration]] minutes`(Google AI), 날짜만 있는 줄(DW 라이브).
- 같은 문장이 두 블록(Verge 부제, Ars 사진 설명) → 같은 번역이 두 번 보임.
- 군더더기가 번역돼 기사처럼 보임: 기자 소개·끝 고지·기부 권유·본문 중간 추천 목록, 메뉴 낱말(BBC 영상·Sounds).
- 표가 빠져(AWS·HF) 번역할 것도 없음 — 표를 살리면 셀 단위 번역이 필요(그때 Translator 에 셀 묶음 보내기 추가).

## 2단계에서 고칠 곳(결정 뒤)

- Translator(이 담당): 케이스 2①(이름 되돌림 표) · 3①(제목 마침표) · 5①(기기 내 흘려 주기 API) · 8 · 10① · 11, 그리고 설정에서 엔진 고르기(자동=지금처럼 기기 내 우선 / 기기 내 / Google).
- Reader 담당(reader-cut)에 인계할 곳: `ArticleExtractor` 의 각주 `sup`(6) · 퍼가기·사진 단추 글(7) · `<br>`(9),
  `ArticleService.run` 이 기기 내 결과를 흘려 받아 바꿔 끼우기(5), 읽기 창의 **문단별 원문 펼치기**(1).
- 시험: 이름 되돌림·짧은 블록 거르기·묶음 대조는 네트워크 없는 단위 시험으로.

**추천: ①.** 표본에서 문단 어긋남은 0이라 구조는 그대로 두고, 눈에 띄는 것(이름 섞임·각주 번호·찌꺼기·느림)을 먼저 줄인다.
기기 내 번역 속도는 한가할 때 다시 재서 5① 의 한도를 정한다.

### 설정 키(윈도우·리눅스도 같은 이름·뜻)

- 키: **`translateEngine`** (상태 파일 `settings` 안, 백업에도 함께)
- 값: `"auto"`(기본) · `"apple"` · `"google"` · `"off"`. 없거나 모르는 값이면 `auto` — 예전 파일·다른 기기에서 온 값도 그대로 읽힘(되돌리기 안전).
- 뜻:
  - `auto` — 맥: 기기 내(Apple) 번역 자료가 있으면 그것, 없거나 실패하면 Google. 윈도우·리눅스: 기기 내 엔진이 없으니 Google.
  - `apple` — 기기 안에서만 번역. 안 되면 원문 그대로, **밖으로 보내지 않음**. 윈도우·리눅스에는 해당 엔진이 없어 고를 수 없게(또는 `off` 처럼) 둔다.
  - `google` — 늘 Google.
  - `off` — 번역하지 않음: 기사 본문·목록 제목 번역도, 같은 소식 비교용 한국어 제목 → 영어 번역(`toEnglish`)도 보내지 않음.
- `apple`·`off` 에서는 `toEnglish` 도 보내지 않는다(같은 소식 묶기는 한국어 제목끼리만 비교하게 됨).

### 인계 — 작업자 Reader(reader-cut)가 고칠 곳

1. **흘려 받아 바꿔 끼우기(케이스 5)**: `ArticleService.run` 의 `translateManyReporting(inputs)` 를
   `translateStreaming(inputs, chunk: 4) { got, engine in … }` 로 바꾸고, `got` 의 번호(입력 배열 기준 — 첫 묶음은 0 이 제목)마다
   `a.blocks[i].original/text` 를 바꿔 `emit`. MainActor 로 넘겨야 한다(`onChunk` 는 Translator actor 에서 불림).
   돌아온 최종 결과로 지금처럼 done/total·엔진 표시를 마무리.
2. **설정이 바뀌면 이미 준비된 기사**: `ArticleService` 의 메모리·디스크 캐시(`articles/*.json`)에는 예전 엔진의 번역이 남는다.
   번역 방식을 바꿨을 때 다시 번역할지(예: 기사 저장 값에 엔진 모드를 적고 다르면 다시 준비) 정할 것. `off` 로 바꾼 뒤 연 기사는 원문으로 보이는 것이 자연스럽다.
3. 추리기 쪽(케이스 6·7·9 와 sources-audit 목록): 각주 `sup` 번호, 퍼가기 코드·사진 단추 글, `<br>`, 중복 블록, 군더더기.
4. 읽기 창 **문단별 원문 펼치기**(케이스 1 — 엔진 오역 확인용).
5. `ArticleService` 가 `Translator.looksForeign` 으로 total 을 세므로 케이스 8 고침으로 숫자뿐 블록 때문에 '일부 번역'이 잘못 붙던 일도 함께 없어진다(손댈 것 없음).
